# PRD: Alertmanager → Slack Relay with Thread/Update-on-Resolve

**Status:** Accepted as context. The open questions in §8 are resolved by
[`001-adr.md`](./001-adr.md); where this document and the ADR disagree (notably the
language choice in §7 and the message-granularity assumption in §5.2), **the ADR wins**.
This file is retained as the problem statement and prior-research record.

**Author context:** Written following a research pass (see "Prior research" below) that
already answered the "should we build this" and "what's the landscape" questions.
Treat those conclusions as settled inputs, not things to re-litigate, unless new
information surfaces.

---

## 1. Problem statement

This cluster's alerting (Prometheus `PrometheusRule` → Alertmanager → Slack, plus one
Grafana-native alert forwarded into the same Alertmanager) only ever posts a **brand
new Slack message** for both the firing and resolved events of the same alert. There is
no message update-in-place and no threaded reply linking a resolution back to the alert
it resolves. In an active channel this makes it hard to tell at a glance what's still
actually firing versus already resolved, and correlating a "RESOLVED" message back to
its original "FIRING" message requires manual scrolling/searching.

Neither Alertmanager nor Grafana's native alerting can do this today, and it's not
close to landing in either upstream project (see prior research). A small,
purpose-built relay sitting between Alertmanager and Slack is the only realistic path.

## 2. Goals

1. When an alert starts firing, post exactly one Slack message for it.
2. When that same alert resolves, either:
   - update the original message in place (status/color changed to resolved), and/or
   - post a threaded reply under the original message announcing resolution,
   correctly correlated via Alertmanager's alert **fingerprint** — not by matching on
   alertname/labels text, which is fragile.
3. Never silently drop a notification because of a bug in the threading/update logic.
   If correlation fails for any reason, the fallback must be "post a new message
   anyway" — this is the alerting path; a silent failure here is the worst possible
   failure mode.
4. Deployable via this repo's existing GitOps conventions (Flux, sops-encrypted
   secrets, the same patterns used for every other app in this repo).

### 2.1 Secondary/optional goal — do not let this dilute goal #1-3

Some other apps in this cluster (Gatus, Home Assistant, kured) each hold their own
sops-encrypted copy of what is functionally the same Slack webhook credential. The
relay *could* also expose a "dumb passthrough" endpoint (forward whatever JSON body it
receives, verbatim, to the real Slack webhook) so those apps stop needing their own
copy of the real secret.

**This is optional, opt-in per app, and explicitly secondary to goals 1-3.** Prior
research concluded sops already handles the secret-duplication problem adequately (it's
a cosmetic/rotation-friction annoyance, not a real security gap), and centralizing
notification delivery for other apps through this relay converts today's four
independent, isolated notification paths into one shared dependency — a new single
point of failure sitting specifically in the alerting/notification path, which is the
worst place to introduce one. If pursued, it must not compromise reliability of the
core alerting use case (e.g., run the passthrough capability with enough redundancy
that its failure doesn't quietly disable Gatus/HA/kured notifications either, and keep
each app's use of it opt-in so a relay outage doesn't unexpectedly dark out paths
someone still cares about).

## 3. Non-goals

- Not replacing Alertmanager's routing, grouping, or **inhibition** rules (this repo
  has real inhibition rules — e.g. suppressing a class of Ceph/etcd alerts during a
  kured-managed reboot — that have no Grafana-native equivalent and are staying on
  Alertmanager regardless of this project).
- Not a full incident-management/on-call platform (i.e., not attempting to become
  Robusta- or PagerDuty-scoped). Single, focused job: correlate firing→resolved and
  reflect that correlation in Slack.
- Not required to solve Alertmanager's own multi-node HA clustering problem (the reason
  in fact makes this a small project — see prior research — is that a standalone
  single-instance relay doesn't have Alertmanager's "which cluster node saw the first
  message" problem at all).
- Not scoped to require Redis or any external dependency beyond a small local/embedded
  state store.

## 4. Prior research (condensed — full findings available in conversation history if needed)

- **Grafana's native Slack notifier cannot do this either.** Verified against
  `grafana/alerting` source: it posts a fresh message every call; the one place it uses
  `thread_ts` is to attach its own screenshot images to the message it just posted, not
  across a resolve. Grafana users requested this exact feature
  ([grafana/grafana#93047](https://github.com/grafana/grafana/issues/93047)); Grafana
  closed it "not planned."
- **Moving alert-notification duty from Alertmanager to Grafana is not a viable
  workaround.** Grafana's contact points only fire for Grafana-*managed* alert rules;
  every `PrometheusRule` in this repo would need to be re-authored as a Grafana-native
  rule to get Grafana's Slack integration involved at all. Grafana Alerting also has
  **no inhibition-rule equivalent**. High migration cost, real capability loss, for the
  same lack of threading.
- **No good existing tool.** `promalert` (kuzaxak/promalert) does exactly this pattern
  but has been abandoned since 2019. Robusta is actively maintained and does Slack
  threading, but as thread-per-*group* summaries in a much heavier full
  incident-response platform — different shape than fingerprint-keyed
  update-in-place, and a large adoption footprint for what's needed here. Grafana
  OnCall is already archived/sunset. PagerDuty/Opsgenie are the wrong category of tool
  (and Opsgenie is EOL).
- **Real demand exists upstream with no resolution in sight**: combined 100+ 👍 across
  the two long-open Alertmanager issues
  ([#2165](https://github.com/prometheus/alertmanager/issues/2165),
  [#3221](https://github.com/prometheus/alertmanager/issues/3221)), continued comment
  activity into 2026, at least one community PoC that stalled awaiting maintainer
  response. Maintainers have said the blocker is Alertmanager's clustered/stateless
  notification design — irrelevant to a standalone relay.
- **This cluster's current architecture already funnels every alert through
  Alertmanager**, including the one Grafana-native alert (it's configured to forward to
  the same Alertmanager via `handleGrafanaManagedAlerts`). This means the relay only
  needs **one** integration point — an Alertmanager webhook receiver — to cover every
  alert source in the cluster today, with no separate Grafana-specific integration
  needed.
- **Passthrough feasibility for other apps** (relevant only if pursuing the optional
  goal in §2.1): Gatus and Home Assistant already emit Slack-shaped JSON bodies to a
  configurable URL, so a dumb-passthrough endpoint needs zero payload translation for
  either. kured is trickier — it hands its webhook URL to the `containrrr/shoutrrr`
  library, whose `slack://` scheme is hardcoded to real Slack's API host (verified in
  shoutrrr's source) and cannot point at an internal relay; kured would need to switch
  to shoutrrr's `generic+http://` scheme (which can point anywhere and can be
  configured to emit Slack-shaped JSON) to be redirectable at all.

## 5. Functional requirements

1. **Alertmanager webhook receiver** (`POST /webhooks/alertmanager` or similar):
   accepts Alertmanager's standard webhook payload (a batch of alerts, each with
   `status: firing|resolved`, `fingerprint`, `labels`, `annotations`, `startsAt`,
   `endsAt`).
2. **On a `firing` alert with a fingerprint not currently tracked**: post a new Slack
   message via `chat.postMessage`; persist `{fingerprint -> {channel, message_ts,
   first_seen}}`.
3. **On a `firing` alert whose fingerprint is already tracked** (Alertmanager's
   `repeat_interval` re-sends firing alerts periodically): decide and document the
   behavior — candidates are (a) no-op, rely on the original message, (b) bump a
   lightweight "still firing" threaded reply, (c) edit the original message's
   timestamp/count. **Open question for the ADR — do not default silently, pick one and
   justify it.**
4. **On a `resolved` alert whose fingerprint is tracked**: look up the stored
   channel/ts, then update the original message in place (e.g. color/status →
   resolved) and/or post a threaded reply announcing resolution. **Open question for
   the ADR**: support both behaviors and make it configurable, or pick one for v1.
5. **On a `resolved` alert whose fingerprint is *not* tracked** (e.g. relay restarted
   and lost state, or was down when the firing notification would have arrived): must
   still surface something in Slack — post a new message rather than silently dropping
   it. Never let missing state cause total silence.
6. **State persistence** must survive pod restarts (routine in this cluster — deploys,
   node reboots). In-memory-only state is not acceptable; recommend a small embedded
   store (SQLite on a small PVC, or an embedded KV like bbolt) — **open question for the
   ADR** on exact technology.
7. **State expiry**: prune fingerprints for long-resolved alerts after some TTL (e.g. a
   few days) to avoid unbounded growth.
8. **(Optional, v1.1+, only if pursuing §2.1) Passthrough endpoint**
   (`POST /webhooks/passthrough` or similar): forwards the received body verbatim to
   the real Slack webhook URL, no interpretation. Should be usable by Gatus and Home
   Assistant with zero changes to their existing Slack-shaped payloads.
9. **Health/metrics**: `GET /healthz` for k8s probes; `GET /metrics` exposing
   Prometheus-scrapeable counters (messages posted, messages updated, threads posted,
   errors by type, current tracked-fingerprint count) — this repo already runs
   kube-prometheus-stack and expects every app to be observable the same way.
10. **Credentials**: needs a real Slack **Bot Token** (`xoxb-...`, `chat:write` scope),
    not an incoming-webhook URL — a different, slightly more involved Slack app setup
    than what's configured today. Store as a sops-encrypted k8s Secret per this repo's
    established convention (plaintext `stringData`, human encrypts before commit).

## 6. Non-functional requirements

- **Never let this become the reason an alert goes unnoticed.** Every failure mode in
  the threading/correlation logic must degrade to "still post a plain Slack message,"
  never to silence.
- Minimal footprint: a single small binary/service, homelab-appropriate resource
  requests, no requirement for Redis or any external dependency beyond local storage.
- Deployable following this repo's conventions: prefer the project's own Helm chart if
  one gets published (matching how Kromgo/Akvorado/etc. were integrated this session);
  otherwise wrap with `bjw-s-labs/app-template` like most other apps here.
- Clear, structured logging — this is the alerting system; failures here need to be
  debuggable quickly.
- If the passthrough feature (§2.1) is built, it must be operable with enough
  redundancy (e.g. 2+ replicas, since that endpoint is stateless) that its own
  reliability doesn't become worse than the status quo for apps that opt into it.

## 7. Rough architecture sketch (non-binding — ADR should confirm or revise)

- Single small service (language TBD by ADR — Go is a reasonable default given
  ecosystem fit: a static single binary, small image, matches other small tools this
  repo has adopted, and has mature Slack SDK support).
- HTTP server exposing the endpoints in §5.
- Local embedded state store (SQLite or similar) on a small `ceph-block` PVC, matching
  how other small stateful apps in this repo are provisioned.
- Slack integration via the real Web API (`chat.postMessage` / `chat.update`) using a
  Bot Token, not a legacy incoming webhook.
- Deployed under `kubernetes/apps/observability/` in this repo (same category as
  Alertmanager/Grafana/kube-prometheus-stack), following this repo's Flux
  `ks.yaml` + `app/` structure.

## 8. Open questions the ADR must resolve

1. Language/framework for the service.
2. Exact behavior for repeat-firing notifications of an already-tracked fingerprint.
3. Update-in-place vs. threaded-reply vs. both, and whether that's configurable or
   fixed for v1.
4. State store technology (SQLite vs. embedded KV vs. something else).
5. Whether to build the optional passthrough/secret-centralization feature (§2.1) in
   v1 at all, or explicitly defer it — leaning toward deferring per prior research.
6. **Where the source code lives and whether to open-source it.** Prior research
   found genuine sustained upstream demand (100+ combined 👍 on the relevant
   Alertmanager issues) and no maintained existing tool occupying this niche — there's
   a real case for building this as a standalone public project rather than
   repo-internal tooling. If so, this affects repo layout: the *code* would likely live
   in its own separate public GitHub repo (not inside this personal home-ops repo),
   while this home-ops repo would only hold the *deployment* manifests for running it,
   the same way any other third-party app is consumed here.
7. Single Slack channel for v1, or per-severity/per-route channel configuration from
   the start?

## 9. Success criteria

- An alert firing produces exactly one Slack message.
- That same alert resolving updates the original message and/or adds a correctly
  correlated threaded reply — no manual scrolling/searching needed to connect the two.
- No alert is ever silently dropped due to a bug or gap in the correlation/threading
  logic.
- (If §2.1 pursued) At least Gatus and Home Assistant can optionally route through the
  relay's passthrough endpoint with no changes to their own payload formats, without
  degrading their own notification reliability.
